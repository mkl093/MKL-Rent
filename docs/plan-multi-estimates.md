# Стенды, версии смет и packing-листы в одном проекте

Сценарий: выставка, несколько стендов (площадок) у одного заказчика. На каждый
стенд своя смета, у сметы может быть несколько версий, и одна из них активна.
На каждый стенд свой packing-лист, плюс один общий packing-лист проекта, где
одинаковое оборудование суммировано.

---

## 0. Зафиксированные требования

| # | Требование | Решение в плане |
|---|---|---|
| 1 | Заказчик один, у стендов разные названия | Заказчик и адрес остаются в проекте. У стенда есть только `name`, он выводится в шапке PDF |
| 2 | Коэффициент задаётся для сметы глобально, строки можно корректировать | `Estimate.rental_coefficient` + флаг `EstimateLine.coefficient_custom` (§4.3) |
| 3 | Сводная смета по проекту в PDF не нужна | Не делаем |
| 4 | Packing-лист отдельный на стенд + общий на проект с суммированием по типу оборудования | Факт ведётся в листах стендов, общий лист собирается из них с суммированием по модели (§4.6) |
| 5 | Галочка «Скрыть стоимость оборудования»: в редакторе цены видны, в документах скрыты | `Estimate.hide_prices`: влияет только на рендер документов. В PDF остаются наименования и количества, «Итого по разделу», коэффициент и общие суммы (§4.4) |
| 6 | Версии смет: не удаляются, одна активная, активная выбирается в модальном окне, просмотр через выпадающий список | Сущность «Стенд» (`ProjectSection`) → версии (`Estimate`) с флагом `is_active` (§4.2) |
| 7 | Заморозка версии, включается отдельно | `Estimate.is_locked`: замороженная версия только для просмотра, её можно сделать активной и скопировать в новую версию, разморозка с подтверждением (§4.2.1) |
| 8 | Факт из packing-листа пишется в смету | Только в активную версию стенда, если она не заморожена (§4.2) |

## 1. Как устроено сейчас (кратко)

- `Estimate` и `PackingList` привязаны к проекту **1:1**: `UNIQUE(project_id)`
  в моделях и миграциях 0004/0005. Около 25 мест вызова находят их по проекту:
  `get_estimate(db, project)`, `get_or_create_estimate`, `get_packing(db, project)`,
  `project_has_packing`. Это `estimates/router`, `packing/service+router`,
  `documents/builder+router`, `transport/service+project_router`,
  `returns/service`, `accessory_kits/project_router+service`, `projects/service`.
- Бронь (`ProjectReservation`) уже считается на проект: `sync_reservations`
  суммирует строки сметы и кабелярку.
- Транспорт ссылается на `packing_line_id`, а не на лист.
- Итоги packing (`packing/calc.py`) считаются по списку строк.
- Коэффициент берётся снимком из `Project.rental_coefficient` в каждую строку при
  добавлении. Отдельного коэффициента у сметы нет. При смене коэффициента
  проекта строки не обновляются.
- PDF сметы (`estimate_pdf.html`) показывает по строкам цену, коэффициент, скидку
  и итог. **Подытогов по разделам (категориям) нет.** `LineGroup` их не считает.
- `GeneratedDocument` уникален по `(project, doc_type, language)`.

### Скрытые проблемы при N листах на проект
1. Проверка уникальности экземпляра (`_auto_assign_quantity_items`, дубль в
   `scan()`, ручной выбор серийника) работает только **внутри одного листа**.
   Один экземпляр сможет попасть в листы двух стендов.
2. Складской `Kit` и `AccessoryKit` физически едут на один стенд. Сейчас
   уникальность проверяется в пределах одной сметы.
3. `copy_estimate` теряет `accessory_kit_id` и `add_to_packing`.

## 2. Целевая модель

```
Project (заказчик, адрес, даты, VAT, коэффициент по умолчанию)
 ├─ ProjectSection «Стенд A»  (номер EST-2026-015)
 │    ├─ Estimate v1
 │    ├─ Estimate v2  ← is_active
 │    ├─ Estimate v3  (черновик альтернативы)
 │    └─ PackingList PCK-2026-031  ← синхронизируется с АКТИВНОЙ версией
 ├─ ProjectSection «Стенд B»
 │    ├─ Estimate v1  ← is_active
 │    └─ PackingList PCK-2026-032
 ├─ AccessoryKit × N        (каждый принадлежит одному стенду)
 ├─ ProjectReservation      = Σ АКТИВНЫХ версий всех стендов + кабелярка
 ├─ Общий packing-лист      = виртуальное объединение листов стендов, Σ по модели
 ├─ Transport               (по строкам всех листов)
 └─ ReturnList              (один на проект, строки с меткой стенда)
```

Принципы:
- **Стенд** (`ProjectSection`, в UI «Стенд / площадка») — раздел проекта. Он
  владеет версиями сметы и packing-листом.
- **Версия** (`Estimate`) — полноценная смета: строки, скидка, коэффициент,
  «скрыть стоимость». Таблица `estimate_lines` не меняется, строки по-прежнему
  ссылаются на `estimates.id`.
- **Только активная версия** влияет на бронь, на packing-лист стенда и на
  документы стенда по умолчанию.
- **Факт сборки** (сканы, серийники, «в упаковке») хранится только в листах
  стендов. Общий лист своих строк не имеет, поэтому синхронизировать «общий ↔
  стендовый» не нужно. Проект с одним стендом и одной версией выглядит почти как сейчас.

## 3. Схема — миграция `0028_sections_versions`

### Новая таблица `project_sections`
| колонка | тип | примечание |
|---|---|---|
| id | PK | |
| project_id | FK projects ON DELETE CASCADE, index | |
| name | VARCHAR(255) NOT NULL | «Стенд A, Hall 3» |
| number | VARCHAR(32) UNIQUE NOT NULL | EST-YYYY-NNN, «номер сметы» стенда |
| sort_order | INT NOT NULL DEFAULT 0 | |
| created_at / updated_at | TimestampMixin | |

### `estimates` (версии)
- Снять `UNIQUE(project_id)`. `project_id` оставить денормализованным (быстрые
  выборки и cascade).
- Добавить:
  - `section_id` FK project_sections ON DELETE CASCADE, NOT NULL после data-migration;
  - `version_no INT NOT NULL`, `UNIQUE(section_id, version_no)`;
  - `label VARCHAR(255) NULL`: комментарий версии («после созвона 12.11»);
  - `is_active BOOL NOT NULL DEFAULT false` + **частичный уникальный индекс**
    `uq_estimates_active_per_section ON estimates(section_id) WHERE is_active`.
    Поддерживается и в PostgreSQL, и в SQLite (`postgresql_where` / `sqlite_where`).
    Это проще циклического FK `section.active_estimate_id`;
  - `activated_at TIMESTAMPTZ NULL`, `created_by_id FK users NULL`;
  - `rental_coefficient NUMERIC(6,3) NOT NULL`, по умолчанию из проекта;
  - `hide_prices BOOL NOT NULL DEFAULT false`;
  - `is_locked BOOL NOT NULL DEFAULT false`, `locked_at TIMESTAMPTZ NULL`,
    `locked_by_id FK users NULL`: заморозка версии (§4.2.1).
- `number` остаётся UNIQUE. У v1 существующих смет номер сохраняется, у новых
  версий пишется `{section.number}-v{N}`. В UI и PDF выводится
  `display_number = "{section.number} · v{N}"`.

### `estimate_lines`
- `coefficient_custom BOOL NOT NULL DEFAULT false`: коэффициент строки
  скорректирован вручную и не перезаписывается при смене коэффициента сметы.

### `packing_lists`
- Снять `UNIQUE(project_id)`. Добавить `section_id` FK project_sections
  `ON DELETE RESTRICT`, `UNIQUE`, NOT NULL после data-migration.

### `generated_documents`
- `scope VARCHAR(32) NOT NULL DEFAULT 'project'`: `project`, `estimate:{id}`
  (версия) или `packing:{id}`.
- Заменить `uq_document_combo` на `UNIQUE(project_id, scope, doc_type, language)`.
  Именно строка, а не nullable FK: в уникальном индексе NULL ≠ NULL, и
  проектные документы задвоились бы.

### `return_lines`
- `section_name VARCHAR(255) NULL`: снимок имени стенда.

### Data-migration
1. На каждый существующий `estimate` создать `project_section`
   (`name='Основной стенд'`, `number=estimate.number`, `sort_order=0`), а в
   самом estimate проставить `section_id`, `version_no=1`, `is_active=true`,
   `rental_coefficient=project.rental_coefficient`, `hide_prices=false`.
2. `estimate_lines.coefficient_custom = (coefficient != project.rental_coefficient)`.
3. `packing_lists.section_id` = секция сметы того же проекта. Если packing есть,
   а сметы нет, создать секцию с пустой версией v1 и номером
   `EST-LEGACY-{project_id}`.
4. `generated_documents.scope` для смет `estimate:{id}`, для остальных `project`.

### Технические риски миграции
- Прод на PostgreSQL. Ограничения из 0004/0005 без имени, поэтому в PG они
  называются `estimates_project_id_key` / `packing_lists_project_id_key`.
  Удалять по имени, найденному через inspector.
- Dev на SQLite (`render_as_batch`). Неименованное ограничение удаляется только
  пересозданием таблицы: `batch_alter_table(recreate="always")` с явным
  описанием таблицы без UNIQUE. Прогнать на копии `dev.db`, потом
  `alembic upgrade head` на `dev.db`.

## 4. Функциональные блоки

### 4.1. Стенды (`app/estimates/sections.py` или внутри `estimates/service.py`)
- `list_sections(project)`, `get_section(project, sid)`.
- `create_section(project, name)` создаёт секцию с номером EST-YYYY-NNN и пустой
  активной версией v1 (коэффициент из проекта).
- `rename_section`, `move_section`.
- `delete_section`: только если у стенда нет packing-листа и **все** его версии
  без строк. Версии не удаляются, поэтому стенд с непустыми версиями удалить нельзя.
- `ensure_default_section(project)` создаёт «Основной стенд» при первом заходе
  в пустой проект. Это заменяет `get_or_create_estimate`, который создавал
  смету молча.

### 4.2. Версии смет
- `list_versions(section)`, `get_active_version(section)`,
  `get_version(section, version_no)`.
- `create_version(section, source: Estimate | None, label, activate=False)`:
  - `source` — версия, которую сейчас смотрит пользователь (по умолчанию
    активная), или `None` для пустой;
  - копирует строки (включая `kit_id`/`accessory_kit_id`: они в пределах того же
    стенда), `discount_percent`, `rental_coefficient`, `hide_prices`,
    `coefficient_custom`, `add_to_packing`;
  - `version_no = max + 1`, номер `{section.number}-v{N}`, `created_by`.
- `activate_version(version)` в одной транзакции снимает флаг со старой
  активной версии, делает `flush` (иначе сработает частичный индекс), ставит
  флаг на новую и заполняет `activated_at`. Затем `sync_reservations(project)`
  и запись в аудит `ESTIMATE_VERSION_ACTIVATE`.
- **Удаления версий нет** ни в сервисе, ни в маршрутах.
- Редактировать можно любую **незамороженную** версию, пока проект не в архиве
  (§4.2.1). Правка неактивной версии не трогает бронь и packing:
  `sync_reservations` читает только активные.
- `preview_activation(version)` для модального окна возвращает:
  - сколько моделей добавится, уберётся или изменится в брони;
  - сколько расхождений появится в packing-листе стенда (через `discrepancies`
    против кандидата).
- Обратная синхронизация packing → смета (`apply_estimate_sync`) пишет факт
  **в активную версию** стенда, как сейчас пишет в единственную смету. Отдельную
  версию для этого не создаём. В окне подтверждения указывается, какая версия
  будет изменена («Стенд A · v2»). Затем `sync_reservations(project)`.
  Если активная версия заморожена, синхронизация недоступна (§4.2.1).

#### 4.2.1. Заморозка версии
Заморозка включается отдельно, кнопкой «Заморозить версию», и автоматически не
срабатывает: ни при генерации PDF, ни при активации, ни при отправке.
- `lock_version(version)` / `unlock_version(version)` заполняют
  `is_locked`/`locked_at`/`locked_by_id` и пишут в аудит
  `ESTIMATE_VERSION_LOCK` / `ESTIMATE_VERSION_UNLOCK`. Разморозка идёт через
  подтверждение «Версия могла быть отправлена клиенту».
- В замороженной версии запрещены любые изменения содержимого:
  - строки: добавить, изменить, удалить, переместить;
  - произвольные строки;
  - скидка, коэффициент сметы, «Скрыть стоимость», комментарий версии;
  - добавление в неё комплекта и кабелярки (со страницы кабелярки тоже);
  - обратная синхронизация packing → смета.

  Проверка стоит в сервисе: общий guard `ensure_editable(estimate)` бросает
  `EstimateLocked`, поэтому обойти её через другой маршрут нельзя. В роутере
  это превращается во флеш-сообщение «Версия заморожена».
- Разрешено:
  - просмотр;
  - PDF;
  - сделать замороженную версию активной;
  - создать новую версию **из** замороженной (копия создаётся незамороженной);
  - создать packing-лист из активной замороженной версии и синхронизировать
    packing по ней (смета → packing читает смету, но не меняет её).
- Заморозка не зависит от архива проекта: архив по-прежнему делает всё
  только для просмотра.
- UI:
  - в выпадающем списке и в модальном окне версий у замороженных значок 🔒;
  - в редакторе поля ввода неактивны, кнопки добавления и правки скрыты;
  - вверху плашка «Версия заморожена {дата}, {кто}» с кнопкой «Разморозить»;
  - в модальном окне версий есть колонка «Заморожена» и кнопки
    «Заморозить» / «Разморозить».

### 4.3. Коэффициент сметы
- `Estimate.rental_coefficient` по умолчанию равен `project.rental_coefficient`
  на момент создания стенда или версии.
- Новые строки (`add_model`, `add_kit_line`, `add_accessory_kit_line`,
  произвольные) получают `coefficient = estimate.rental_coefficient`,
  `coefficient_custom=False`. Сейчас кабелярка создаётся с коэффициентом 1. Это
  стоит выровнять (цена у неё и так 0 по умолчанию).
- `set_estimate_coefficient(estimate, value)` перезаписывает `coefficient` во
  всех строках с `coefficient_custom=False`. Скорректированные вручную строки
  не трогаются.
- `update_line`: если введённый коэффициент отличается от коэффициента сметы,
  ставится `coefficient_custom=True`. Кнопка «↺» у строки сбрасывает к
  коэффициенту сметы.
- UI: поле «Коэффициент сметы» рядом со скидкой. У строк с ручным
  коэффициентом подсветка и значок «изменён».
- `Project.rental_coefficient` остаётся значением по умолчанию для новых
  стендов и версий. Его изменение существующие сметы не трогает: смета — свой
  документ.
- PDF: коэффициент сметы в шапке или блоке итогов. В обычном режиме колонка
  коэффициента у строк остаётся.

### 4.4. «Скрыть стоимость оборудования»
- `Estimate.hide_prices` — галочка на странице сметы, своя у каждой версии.
- **Флаг влияет только на рендер документов, но не на редактор.**
  - В редакторе сметы (`estimates/estimate.html`, подбор оборудования, строки)
    цена, коэффициент, скидка и итог строки видны и редактируются всегда,
    независимо от галочки. Рядом с галочкой подсказка «В документах будут
    показаны только итоги по разделам».
  - Скрытие применяется в одном месте: в рендере сметы для документов
    (`documents/builder._estimate_render` → `estimate_pdf.html`) для всех
    языков (ru/en/de). Любой будущий вывод сметы клиенту (печать, HTML-превью,
    экспорт) должен идти через этот же рендер и уважать `hide_prices`.
- `LineGroup` получает `subtotal` (сумма `line_total` строк раздела).
  `grouped_lines` считает его.
- PDF (`estimate_pdf.html`) при `hide_prices`:
  - колонки: **Наименование, Кол-во** (количество остаётся видимым). Цена,
    коэффициент, скидка строки и итог строки скрыты;
  - после каждого раздела (категория, «Комплекты», «Комплекты аксессуаров»,
    «Прочее») идёт строка **«Итого по разделу «Свет»: …»**
    (en: *Subtotal «Lighting»*, de: *Zwischensumme «Licht»*);
  - блок итогов: **коэффициент сметы**, подытог, общая скидка (если > 0), VAT,
    итого.
- В обычном режиме PDF не меняется.
- `hide_prices` и `rental_coefficient` входят в fingerprint PDF, чтобы
  документ помечался устаревшим.
- Локализация: новые ключи `L.group_subtotal` («Итого по разделу» / «Subtotal» /
  «Zwischensumme») и `L.coef_estimate` в `documents/l10n.py`.

### 4.5. Бронь и уникальность комплектов
- `sync_reservations(db, project)` без аргумента `estimate` суммирует строки
  **активных версий всех стендов** + содержимое кабелярки. Обновить все вызовы.
- Складской `Kit` и `AccessoryKit` принадлежат одному стенду. Добавить их можно
  в любую версию этого стенда, но не в версии другого стенда. Проверка идёт по
  `estimate_lines JOIN estimates WHERE project_id=… AND section_id != …`, в
  сообщении указывается имя стенда-владельца. Так переключение активной версии
  никогда не создаёт конфликт брони комплектов.
- В подборе оборудования (`estimates/add.html`) показывать «в этой версии: N /
  в проекте (активные): M». Доступность считается как сейчас, без учёта
  текущего проекта.

### 4.6. Packing-лист стенда (`app/packing/service.py`)
- `get_packing(db, project)` заменить на `get_packing(db, packing_id)`,
  `get_section_packing(db, section)` и `list_packings(db, project)`.
  `project_has_packing` сохраняет смысл «хотя бы один лист».
- `create_from_estimate(db, section)` строит лист из **активной** версии стенда.
- `_estimate_*` helpers, `discrepancies`, `sync_removals`, `apply_sync`,
  `estimate_discrepancies`, `apply_estimate_sync` работают в паре
  `(активная версия стенда, лист стенда)`.
- **Уникальность экземпляров на проект:**
  - `_project_used_item_ids(db, project_id)` — один JOIN
    `packing_serial_items → packing_lines → packing_lists`;
  - используется в `_auto_assign_quantity_items`, `scan()`, `add_serial_item()`
    и списке выбора серийника;
  - новый `SerialResult.IN_OTHER_PACKING`: «Экземпляр уже в packing-листе
    «Стенд B»». Заготовку (`confirmed_by_scan=False`) из чужого листа реальный
    скан может перетянуть к себе: там она освобождается, и `backfill` подберёт
    другой экземпляр.
- `scan()` при `WRONG_MODEL` подсказывает: «Модель есть в packing-листе
  «Стенд B»». В чужой лист автоматически не пишем.
- `add_accessory_kit(packing, kit)` разрешён только в лист стенда-владельца
  кабелярки.
- Статус остаётся у листа. В карточке проекта показывается агрегат: минимум из
  статусов листов стендов.

### 4.7. Общий packing-лист проекта (суммирование по модели)
Новый модуль `app/packing/combined.py`:
```python
@dataclass
class CombinedLine:
    key: tuple                     # ("model", id) | ("kit", id) | ("akit", id) | ("custom", line_id)
    sources: list[PackingLine]     # строки листов стендов
    by_section: list[tuple[str, int]]   # [("Стенд A", 4), ("Стенд B", 2)]
    name, category_name, subcategory_name, is_serial, …
    planned_quantity / fact_quantity / packed_quantity   # суммы
    serial_items                    # объединённые штрих-коды/S/N
    calc: LineCalc                  # СУММА LineCalc источников

def combined_packing(db, project) -> CombinedPacking   # lines, totals, breakdown, accessories
```
- Складские модели **сливаются по `model_id`**: план, факт и «в упаковке»
  суммируются, штрих-коды объединяются, колонка «Стенды» показывает
  распределение («A: 4 · B: 2»).
- Упаковка, вес и объём считаются **суммой `LineCalc` источников**, а не
  пересчётом от суммарного количества: кейсы стендов физически разные.
- Комплекты, кабелярка и произвольные строки не сливаются и получают метку стенда.
- Итоги и разбивка по категориям — существующие `compute_totals` /
  `compute_category_breakdown`, адаптированные под `CombinedLine` (или поверх
  `LineCalc`).
- Страница `/projects/{pid}/packing` (только чтение):
  - сверху таблица листов стендов: номер, стенд, активная версия сметы, статус,
    факт/план, вес, кнопки «Открыть» / «Создать из сметы»;
  - ниже общий лист и общие итоги (вес, объём, питание, кейсы, кабелярка).

### 4.8. Документы (`app/documents/`)
- `render_html(..., scope)`:
  - `ESTIMATE` — по версии сметы. В шапке: заказчик проекта, **название стенда**,
    `display_number`, `hide_prices`;
  - `PACKING` / `PICKING` — по листу стенда или по проекту (общий, суммированный);
  - `TRANSPORT` — только по проекту.
- `generate` / `get_document` / `status` / путь хранения учитывают `scope`.
  Файл `{doc_type}_{scope}_{lang}.pdf`, при скачивании
  `{doc_type}_{PRJ}_{Стенд}[_v{N}]_{lang}.pdf`.
- Страница «Документы»:
  - блок на каждый стенд: смета активной версии + packing + picking стенда;
  - блок «Проект целиком»: общий packing, picking, transport, carnet;
  - PDF неактивной версии формируется со страницы сметы кнопкой «PDF этой версии».
- Carnet по проекту (общий) и по стенду. `carnet.build_rows` принимает список строк.
- Fingerprint включает имя стенда, номер версии, коэффициент сметы и `hide_prices`.
- Учесть отступления от ТЗ в `packing_pdf.html`: ДхШхВ вместо объёма и
  подобранные под WeasyPrint ширины колонок. В общий лист добавляется колонка
  «Стенды», ширины придётся перепроверить на реальном WeasyPrint.

### 4.9. Транспорт и приёмка
- `transport_service.board(project)` строится по строкам `list_packings(project)`,
  пул нераспределённого сгруппирован по стенду. `TransportAssignment` не меняется.
- Приёмка одна на проект: `create_from_packing` идёт по всем листам и
  проставляет `ReturnLine.section_name`. На странице строки сгруппированы по стенду.

### 4.10. Копирование проекта
- Копируются стенды (имена, порядок) и **только активные версии** (становятся
  v1 копии). Неактивные версии не копируются.
- Строки с `accessory_kit_id` пропускаются (кабелярка проектная). Заодно
  исправляется потеря `add_to_packing` / `coefficient_custom`.

## 6. Тесты
- **Миграция:** upgrade на снимке с существующей сметой и packing дает
  секцию, v1 активна, `packing.section_id` проставлен, `coefficient_custom` верен.
- **Стенды:** создание, удаление пустого, запрет удаления непустого.
- **Версии:**
  - копирование строк;
  - одна активная (частичный индекс; конкурентная активация падает на индексе);
  - заморозка: все мутации сервиса бросают `EstimateLocked`, маршруты отвечают
    флешем без изменений; замороженную версию можно активировать и скопировать;
    обратная синхронизация в замороженную активную версию запрещена;
    разморозка снимает запрет;
  - активация пересчитывает бронь;
  - неактивная версия не влияет на бронь;
  - удаления нет;
  - номера `-vN`.
- **Коэффициент:** смена коэффициента сметы обновляет только
  не-custom строки; ручная правка ставит custom; сброс.
- **Скрыть стоимость:** «Итого по разделу», PDF без цен (проверка HTML на всех
  языках), редактор сметы при включённой галочке по-прежнему показывает цены,
  изменение fingerprint.
- **Комплекты:** Kit и кабелярка не попадают в смету другого стенда, но
  попадают в другую версию своего стенда.
- **Packing:**
  - лист на стенд по активной версии;
  - синхронизация не задевает соседний лист;
  - экземпляр нельзя отсканировать или назначить в два листа;
  - авто-заготовки не пересекаются;
  - заготовка перетягивается сканом;
  - после смены активной версии видны расхождения.
- **Общий лист:** суммирование по модели, распределение по стендам, объединение
  штрих-кодов, упаковка как сумма `LineCalc`, комплекты не сливаются.
- **Документы:** scope в уникальности, устаревание per scope, PDF неактивной версии.
- **Транспорт и приёмка:** данные из двух листов, `section_name`.
- **Web:** новые маршруты, модальное окно активации, выбор версии,
  редиректы совместимости, проект с одним стендом.

## 9. Шаг 4 — детальный план (общий packing-лист проекта)

### 9.1. Когда есть общий лист
- Общий лист — **только чтение**, собирается на лету из листов всех стендов,
  в БД не хранится (миграции нет).
- Показывается, когда у проекта **≥ 2 packing-листов**. При одном листе он
  совпадал бы с листом стенда: `/projects/{pid}/packing` по-прежнему ведёт на
  лист стенда, на странице «Документы» блока общего листа нет.
- Стенды без листа в общий лист не входят; на странице это видно в таблице
  стендов («не создан»).

### 9.2. Сборка (`app/packing/combined.py`)
- `CombinedLine` повторяет атрибуты `PackingLine`, которые читают шаблоны
  (`name`, `is_custom/is_kit/is_accessory_kit`, категория/подкатегория, габариты,
  упаковка, `comment`, `serial_items`, план/факт/в упаковке), плюс:
  - `sources` — строки листов стендов;
  - `by_section` — `[("A", 4), ("B", 2)]` по факту (план — если факта нет);
  - `calc` — **сумма `LineCalc` источников** (кейсы стендов физически разные,
    поэтому упаковки/вес/объём не пересчитываются от суммарного количества).
- Слияние:
  - строки складских моделей — по `model_id`: план, факт, «в упаковке»
    суммируются, штрих-коды/S/N объединяются;
  - комплекты, кабелярка и произвольные строки **не сливаются**, получают
    метку своего стенда.
- Порядок и группировка — как в листе стенда (категория → подкатегория → имя).
- `combined_packing(db, project) -> CombinedPacking`: `packings`, `lines`,
  `totals`, `breakdown`, `accessories` (сумма по всем листам), `shortages`
  (`[(стенд, комментарий)]`), `status` — минимальный из статусов листов.
- `calc.py`: `compute_totals` / `compute_category_breakdown` получают вариант
  поверх готовых пар `(строка, LineCalc)`, чтобы общий лист и лист стенда
  считались одним кодом. `accessory_totals` принимает список строк.

### 9.3. Веб: `/projects/{pid}/packing` (при ≥ 2 листах)
- Сверху — текущая таблица стендов + строка «Итого по проекту»
  (факт/план, вес, общий статус).
- Ниже — общий лист по категориям: Наименование · Стенды («A: 4 · B: 2»,
  ссылки на листы) · План · Факт (недостача красным) · В упаковке / упаковок ·
  Вес · Объём. Штрих-коды не выводятся (они на листах стендов).
- Под ним — разбивка по категориям, аксессуары, итоги (вес, объём, питание),
  недостачи по стендам.
- Кнопки: PDF общего packing-листа и листа комплектации, общий carnet.
- Карточка проекта: кнопка «Packing-лист» при ≥ 2 листах называется
  «Packing-листы (общий)».

### 9.4. Документы
- `PACKING` / `PICKING` с `packing=None` = **общий лист проекта**, scope
  `"project"` (после миграции 0031 этот scope у packing/picking свободен).
  `generate`/`render_html` больше не подставляют «лист первого стенда».
- Файл хранения — `{type}_all_{lang}.pdf`: имена `packing_{lang}.pdf` остались
  у перенесённых в 0031 документов стендов, их нельзя перезаписать. Имя при
  скачивании — `{type}_{PRJ}_all_{lang}.pdf`.
- PDF общего packing-листа: заголовок «Packing-лист PRJ-… — все стенды»,
  строка «Стенды: A (PL-…), B (PL-…)», новая колонка «Стенды»; S/N — объединённые.
  Ширины колонок перераспределяются и проверяются на реальном WeasyPrint.
- PDF общего листа комплектации: план/факт суммой, место хранения, колонка
  «Стенды».
- Отпечаток (fingerprint) — по всем источникам и названиям стендов; общий PDF
  устаревает при изменении любого листа.
- `combined_status(db, project)` для страницы «Документы»; блок «Проект
  целиком»: общий packing, общий picking, packing по машинам, общий carnet.
- Ярлыки ru/en/de: «все стенды», «Стенды».

### 9.5. Carnet проекта
- `carnet.build_rows(db, lines)` принимает список строк (лист стенда или общий).
- Общий carnet: строки одной модели из разных стендов **сливаются** (кол-во
  суммой, S/N — общим списком), комплекты и кабелярка разворачиваются по
  составу, как сейчас. Шапка: «Packing-листы: PL-… (A), PL-… (B)».
- `/documents/carnet` — общий при ≥ 2 листах, иначе лист единственного стенда;
  `/documents/carnet/{packing_id}` — лист стенда (без изменений).

### 9.6. Прочее
- Downgrade миграции 0031: перед возвратом scope `"project"` удалять записи
  общих packing/picking (иначе конфликт уникальности).
- Legacy-маршруты `/documents/{packing|picking}/{lang}/view|download` теперь
  отдают общий лист.

### 9.7. Тесты
- Слияние по модели: суммы план/факт/в упаковке, `by_section`, объединение
  штрих-кодов; упаковки/вес/объём = сумма `LineCalc` (пример, где пересчёт от
  суммы дал бы меньше кейсов).
- Комплекты, кабелярка, произвольные строки не сливаются и помечены стендом.
- Итоги, разбивка, аксессуары, недостачи, общий статус.
- PDF общего packing/picking: колонка «Стенды», имя файла `_all_`, не
  перезаписывает файл стенда; устаревание при изменении листа стенда; ru/en/de.
- Carnet: общий со слиянием модели, по стенду — без изменений.
- Web: обзор с общим листом при двух листах, редирект при одном, блок
  «Проект целиком» на «Документах».
- Прогон на PostgreSQL (как в шагах 2–3).
